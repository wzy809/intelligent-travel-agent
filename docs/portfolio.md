# 智能旅行规划 Agent 作品集说明

## 1. 项目概述

智能旅行规划 Agent 是一个面向年轻自由行用户的 AI 旅行规划产品原型。它聚焦一个具体场景：用户已经从小红书、抖音、携程等平台收藏了很多想去的地点，但不知道如何筛选、分组、安排顺路路线。

本项目通过“App 式对话入口 + Agent 逐步追问 + 路线方案生成 + 对话修改”的方式，帮助用户把零散旅行灵感转化为真实可执行的每日旅行计划。

项目当前支持 Demo Mode 和 LLM Mode：

- Demo Mode：无需 API Key，可直接运行，使用本地规则引擎展示完整流程。
- LLM Mode：配置 OpenAI API Key 后，可调用大模型生成真实旅行方案。

## 2. 项目背景

年轻自由行用户并不是不会做攻略，而是经常被信息淹没。

他们会在小红书、抖音、携程等平台收藏大量地点、笔记、视频和推荐，但真正规划路线时会遇到几个问题：

- 收藏地点太多，不知道哪些值得去。
- 多个地点看起来都不错，但不知道如何取舍。
- 景点、餐厅、街区之间距离不清楚，容易绕路。
- 营业时间、价格、预约规则不确定，导致计划不可执行。
- 用户有个性化偏好，比如不想早起、不想太累、一定要去某些地点。

因此，本项目没有选择做“泛旅行攻略生成器”，而是选择一个更具体的切口：

> 帮用户整理已收藏地点，并生成可执行路线。

## 3. 目标用户

核心用户为 20-35 岁年轻自由行用户。

典型用户画像：

- 有自由行意愿，不倾向跟团。
- 会主动查攻略，但容易信息过载。
- 常用小红书、抖音、携程获取旅行灵感。
- 经常收藏很多地点，但出发前需要花大量时间整理。
- 希望旅行既个性化，又不要太累、太绕、太不确定。

## 4. 核心痛点

### 4.1 信息过载

用户在多个平台收藏了很多地点，但信息分散、重复、真假难辨。

### 4.2 决策疲劳

地点太多后，用户不知道该保留哪些、放弃哪些，也不知道哪些地点体验相似。

### 4.3 路线拼接困难

单个地点看起来都不错，但放到每天路线中可能出现跨区绕路、时间过满、交通不顺等问题。

### 4.4 可实施性不足

普通 AI 行程经常忽略营业时间、价格、预约、首尾日到达离开时间，导致路线看起来合理但实际难以执行。

## 5. 产品定位

本产品定位为：

> 面向年轻自由行用户的 AI 攻略共创助手，帮助用户把收藏地点整理成可执行、可解释、可修改的旅行路线。

它不是传统 OTA，也不是简单聊天机器人，而是一个具备规划能力的旅行 Agent。

## 6. MVP 范围

当前 MVP 支持：

- App 式首页输入。
- 文本、截图、链接三种导入入口。
- Agent 逐步追问旅行信息。
- 收集出行城市、日期、到达时间、离开时间、同行人数、预算、必去地点、旅行节奏、交通偏好、酒店区域。
- 地点识别与本地 POI 补全。
- 营业时间、价格、预约信息的置信状态展示。
- 生成 1-3 套旅行方案。
- 根据用户节奏默认推荐方案。
- 支持用户继续对话修改，比如“第二天太累了”“预算降一点”“不要早起”。
- 支持确认最终方案。

当前暂不支持：

- 真实机票、酒店、门票预订。
- 平台账号收藏同步。
- 实时地图导航。
- 实时价格锁定。
- 多人协同投票。

## 7. 核心产品流程

```text
用户输入旅行想法 / 收藏地点
  ↓
Agent 创建旅行规划会话
  ↓
逐步追问关键信息
  ↓
识别并补全地点信息
  ↓
生成路线诊断
  ↓
输出 1-3 套路线方案
  ↓
用户对话修改
  ↓
确认最终行程
```

## 8. Agent 设计原则

### 8.1 用户需求优先

用户标记为必去的地点默认必须保留。即使路线存在冲突，Agent 也不能擅自删除，而是要说明代价并请用户确认。

### 8.2 真实可执行优先

路线生成必须考虑：

- 到达和离开时间。
- 地点距离和交通顺路性。
- 营业时间。
- 门票或消费水平。
- 是否需要预约。
- 用户体力和旅行节奏。

### 8.3 主动指出不合理

Agent 不应该只迎合用户，而要主动指出：

- 一天安排过满。
- 地点跨区太远。
- 相似地点重复。
- 预算可能超出。
- 营业时间或预约存在风险。

### 8.4 轻微问题直接优化，重大冲突必须确认

轻微问题如地点顺序不佳、轻微绕路，可以由 Agent 直接优化。

重大冲突如必去地点闭馆、首尾日时间不足、预算明显超出，必须让用户确认。

### 8.5 不确定信息必须展示置信状态

营业时间、价格、预约规则可能变化，不能伪装成确定信息。当前设计中使用：

- 已确认
- 待确认
- 可能变化

## 9. 功能亮点

### 9.1 从模糊输入开始

用户不需要一开始填写完整表单，可以直接说：

> 我想和朋友去上海玩 3 天，收藏了外滩、武康路、上海博物馆，不想太累。

Agent 会逐步追问缺失信息。

### 9.2 支持多来源导入

产品入口保留年轻用户常用信息源：

- 小红书
- 抖音
- 携程

当前 Demo 支持文本、截图、链接三种入口。截图和链接已保留接口，后续可接 OCR 和平台解析能力。

### 9.3 多方案但不重复提问

用户在追问阶段选择的是“默认旅行节奏”，不是最终方案。结果页会优先展示匹配方案，其他方案作为备选。

### 9.4 可解释路线

每个地点安排都包含原因或注意事项，例如：

- 用户必去。
- 同区域顺路。
- 适合夜景时段。
- 价格需要确认。
- 预约规则可能变化。

### 9.5 Demo Mode + LLM Mode

为了应聘展示和低成本运行，项目支持两种模式：

- 未配置 API Key：使用本地规则引擎，完整展示产品流程。
- 配置 API Key：调用 OpenAI API，由 LLM 生成真实旅行方案。

这体现了产品验证阶段对成本、可演示性和可扩展性的考虑。

## 10. 技术实现

### 10.1 项目结构

```text
travel-agent-app/
  server.py
  requirements.txt
  public/
    index.html
    styles.css
    app.js
```

### 10.2 前端

前端为原生 HTML、CSS、JavaScript 实现，重点是快速验证交互流程。

页面包括：

- App 首页。
- Agent 追问页。
- 每日规划结果页。
- 方案切换。
- 对话修改。

### 10.3 后端

后端使用 Python 实现，提供 API 和静态页面服务。

核心接口：

```text
POST /api/import/text
POST /api/import/image
POST /api/import/link
POST /api/sessions
POST /api/sessions/{session_id}/answers
POST /api/sessions/{session_id}/plans
POST /api/sessions/{session_id}/revise
POST /api/sessions/{session_id}/confirm
```

### 10.4 LLM 接入

后端支持 OpenAI API：

- 通过 `OPENAI_API_KEY` 读取密钥。
- 通过 `OPENAI_MODEL` 配置模型。
- 要求 LLM 输出固定 JSON 结构。
- 后端对 LLM 输出做结构校验和归一化。
- 调用失败时自动回退到规则版方案。

## 11. 项目价值

这个项目的价值不只是“生成一份旅行计划”，而是完整展示了一个 AI 产品从痛点识别到 Agent 工作流设计的过程。

作为产品经理作品，它体现了：

- 用户洞察能力。
- MVP 范围控制能力。
- Agent 交互设计能力。
- 复杂场景拆解能力。
- 对 AI 幻觉和数据不确定性的风险意识。
- 前后端协作与接口设计意识。
- 对真实商业化产品后续迭代路径的理解。

## 12. 后续迭代计划

### 12.1 接入地图 POI

接入高德地图、百度地图或 Google Maps，实现真实地址、坐标和距离判断。

### 12.2 接入交通耗时

根据真实交通方式计算步行、地铁、打车时间，避免路线绕路。

### 12.3 接入 OCR

支持用户上传小红书、抖音、携程截图后自动识别地点。

### 12.4 接入搜索能力

补充营业时间、门票价格、预约规则、热门时段等信息。

### 12.5 支持多人协同

多人出行时支持偏好收集、冲突识别和方案折中。

### 12.6 旅行中陪伴模式

从“出发前规划”扩展到“旅行中实时调整”，如天气变化、景点闭馆、临时想换餐厅等。

面试时可以这样介绍：
